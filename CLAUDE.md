# RemindersInt

## Vision
App iOS native de rappels à saisie vocale ultra-rapide. Le problème : les micro-tâches orales ("rappelle-moi d'appeler Karim") se perdent parce que les saisir dans Rappels ou Calendrier coûte trop cher sur le moment.
Promesse : capturer un rappel en moins de 3 secondes depuis l'écran verrouillé, et être relancé jusqu'à ce que ce soit fait.

## Utilisateur V1
Un seul utilisateur : le développeur, sur son iPhone 17 Pro Max, installé via Xcode avec un Apple ID gratuit. Pas d'App Store, pas de backend, pas de compte.

## Métrique de succès V1
Après une semaine d'usage réel : l'app est toujours utilisée chaque jour, et le nombre de rappels oubliés a baissé.

## Hors périmètre (interdit sans demande explicite)
Comptes, synchronisation, cloud, partage, Android, pièces jointes, Siri, Apple Watch, widgets écran d'accueil autres que celui décrit, dark mode custom, onboarding, analytics, dépendances externes.

## Stack imposée
- iOS 26+, SwiftUI, Swift 6, Xcode 26
- Persistance : SwiftData (modèle local uniquement)
- Notifications : UserNotifications (locales, avec UNNotificationCategory et actions)
- Voix : Speech framework (SFSpeechRecognizer, fr-FR, uniquement sur l'appareil : sans modèle hors ligne, pas de dictée)
- Extraction : Foundation Models framework (LanguageModelSession + @Generable), on-device, pas d'API cloud
- Widget : WidgetKit + AppIntents (iOS 17+), pour le bouton écran verrouillé
- Aucune dépendance Swift Package externe

## Architecture
- Dossiers : Models / Views / ViewModels / Services / Widget
- Modèles SwiftData (V2, étape 6a) :
  - TaskItem (la « Task » du plan ; nommée ainsi car `Task` masquerait Swift Concurrency)
    - id: UUID, title: String, dueDate: Date?, repeatInterval: enum RepeatInterval { none, every5min, every15min, every30min, hourly }
    - status: enum ReminderStatus { pending, done, cancelled }, createdAt: Date, remindersSent: Int
    - rawTranscript: String? (ce qui a été dicté, conservé en DEBUG uniquement), note: String?
    - isReminder: Bool (true = rappel avec relances comme en V1 ; false = tâche, une seule notification à l'échéance si elle existe)
    - space: Space?
  - Space : id, name, colorHex, sfSymbol, sortOrder, isArchived, createdAt, parent: Space?, children (cascade), tasks (nullify). Arbre à profondeur illimitée, un seul parent.
  - Session (étape 6b) : id, space (toujours renseigné ; optionnel côté SwiftData), startedAt, endedAt?, note?, rawTranscript?. Une seule session ouverte (endedAt == nil) à la fois. Une session fermée ne passe jamais minuit : elle est coupée à la clôture, à l'enregistrement et à la modification, sauf une séance de muscu, qui garde sa session entière (durée et volume) ; les totaux par jour la répartissent par chevauchement.
  - Goal (étape 6c, 7b) : id, space (toujours renseigné), title, kind { hours, count, outcome, prWeight }, exerciseID? (prWeight), target, unit?, period { week, month, untilDate, none }, deadline?, currentManual, counterPeriodStart?, isAchieved, achievedAt?, createdAt, isArchived, steps: [GoalStep { id, title, isDone, sortOrder }]. Calculs dans `GoalMath`.
  - Space.module : SpaceModule? (nil = aucun), voir « Modules ».
  - PrayerSettings (étape 7a, une par espace au module prayer) : latitude, longitude, cityName, hasLocation, method { franceMuslims12, mwl, ummAlQura, isna, egypt, karachi }, asrMadhab { shafi, hanafi }, un ajustement en minutes par prière, notifyAtAdhan, repeatUntilDone, repeatInterval, quietMode, activatedAt.
  - PrayerRecord (étape 7a) : id, date (début du jour), prayer { fajr, dhuhr, asr, maghrib, isha }, status { pending, onTime, late, missed, madeUp }, checkedAt?. Global (pas lié à un espace) : un seul module Prière actif à la fois.
  - Exercise (étape 7b) : id (slug de la bibliothèque ou `custom-<uuid>`), nameFR, nameEN, aliases, muscleGroup { chest, back, shoulders, biceps, triceps, legs, glutes, core, cardio, other }, kind { weightReps, bodyweightReps, time, distance }, isCustom. Bibliothèque de 60 exercices bilingues dans `Resources/exercises.json`, installée et mise à jour au lancement (`ExerciseLibrary`).
  - WorkoutTemplate { id, name, sortOrder, items: [TemplateItem { order, exercise, targetSets, targetReps, targetWeight?, restSeconds }] } (7b). Programmes de démo Push A, Pull A, Legs A posés à l'activation du module.
  - Workout (7b) : id, session (une séance EST une Session de l'espace Salle), template?, currentOrder, restEndsAt?, entries: [WorkoutEntry { order, exercise, cibles copiées du programme, restSeconds, sets: [WorkoutSet { reps?, weightKg?, seconds?, meters?, isPR, completedAt }] }]. Records calculés (`GymMath`) : charge max, reps max à une charge, volume max d'une séance, 1RM estimé Epley = w × (1 + reps / 30).
  - Reminder : modèle V1 conservé uniquement comme stockage hérité, vidé au lancement par `StoreSetup` (voir Décisions).
- Services :
  - NotificationService : planifie, annule et replanifie les notifications locales des TaskItem en attente et datés ; relances selon repeatInterval pour les rappels, notification unique pour les tâches
  - SpeechService : transcription voix -> texte
  - ParserService : texte -> ParsedCapture via Foundation Models : intention (reminder / task / sessionStart / sessionStop / sessionLog / goalProgress / prayerCheck / gymSet / gymNext / gymFinish / gymStart), titre, date/heure absolue, intervalle de relance, jusqu'à 3 espaces probables avec confiance. Date de référence = maintenant, dans le fuseau de l'appareil, français. Un rappel sans date fait demander la date plutôt que d'inventer ; une tâche peut rester sans date.
  - SpaceRouter : routage de secours par mots-clés sur les noms d'espaces et leurs synonymes. Seuil de confiance 0,6.
  - TrackingService : démarrer / arrêter / enregistrer / modifier une session, Live Activity (ActivityKit, mise à jour locale), notification « Toujours sur … ? » après 4 h, rappel « Rien tracké aujourd'hui » à 20 h.
  - PrayerTimesCalculator (7a) : horaires en Swift pur (déclinaison, équation du temps, angles Fajr / Isha par méthode, Asr selon le madhab, règle par angle aux hautes latitudes, ajustements). Testé dans `RemindersIntTests` (schéma partagé `RemindersIntTests`).
  - PrayerService (7a) : statuts automatiques, stats, notifications d'adhan et relances, instantané App Group pour le widget « Prochaine prière » et le contrôle « Prière faite ». PrayerLocator : CoreLocation une fois, recherche de ville MKLocalSearch.
  - GymService (7b) : démarrer (programme ou séance libre) / terminer une séance via TrackingService, séries (ajout, copie, édition, suppression), PR recalculés dans l'ordre chronologique, exercice suivant, chrono de repos et sa notification, résumé, ligne Salle de la Live Activity. GymMath (calculs purs) et GymParsing (règles de dictée FR / EN) sont testés dans `RemindersIntTests`.

## Modules
Un Space peut activer un module (`enum SpaceModule { none, prayer, gym }`, stocké en optionnel pour une migration légère). Un module ajoute un écran dédié en haut de `SpaceDetailView` et des données structurées, sans retirer tâches, temps et objectifs. Activation à la création de l'espace (sélecteur « Module ») ou depuis le menu « … » du détail ; désactivation dans le même menu ou les réglages du module (l'historique reste).
- prayer (7a) : horaires, coche des 5 prières, statuts, stats, notifications, widget et contrôle. Un seul espace à la fois.
- gym (7b) : programmes, séance en cours (maquette 12), séries et PR, repos, historique et courbes par exercice, intentions vocales gym.*, objectifs « séances par semaine » et « charge cible ». Un seul espace à la fois. `ContributionGrid` (Views/Components) est générique : `[Date: Double]` 0...1, couleur, nombre de semaines.

## Décisions prises en cours de route

- Étape 3 : `Date` n'est pas `@Generable`, le modèle renvoie une date ISO `AAAA-MM-JJTHH:MM` convertie ensuite. Parser de secours en Swift pur si Foundation Models est indisponible ou échoue (note dans Réglages). Champ « Simuler une dictée » en DEBUG uniquement.
- Étape 4 : option A retenue, un ControlWidget (`ControlWidgetButton` + `StartVoiceCaptureIntent`, `openAppWhenRun`) placé en bas de l'écran verrouillé ou dans le Centre de contrôle. Vérifié sur simulateur via le Centre de contrôle : un tap lance l'app fermée directement sur la dictée. iOS impose le premier plan pour le micro : depuis l'écran verrouillé, le tap déclenche Face ID puis l'app s'ouvre déjà en écoute ; il n'existe pas de dictée sans déverrouiller.
- Étape 4 : deep links `remindersint://capture` et `remindersint://reminder/<uuid>`. Widget `accessoryRectangular` « Prochain rappel » alimenté par un instantané JSON écrit par l'app dans l'App Group `group.com.yacine.RemindersInt` (le widget ne lit pas SwiftData). Code commun app/extension dans `Shared/`.
- Étape 5 (polish) : cible iOS 26.5, donc `.glassEffect` partout, aucun fallback Material. La dictée n'est plus une feuille mais un panneau superposé dans `ContentView` (app floutée et assombrie dessous, ressort depuis le bas, fermeture par tap sur le fond ou glissement vers le bas). Onglets en icônes seules, libellés en accessibilité. Ressort commun `Animation.appSpring` ; l'ouverture des feuilles système garde l'animation iOS (non personnalisable). Arguments DEBUG pour les captures : `-uiTab day|month|settings`, `-uiScreen capture|detail|form`.

- Étape 6a : SwiftData ne sait pas renommer une entité. `Reminder` reste dans le schéma (ajout de `TaskItem` et `Space` = migration légère additive) et `StoreSetup.run`, appelé dans `App.init` avant toute réponse de notification, copie chaque Reminder en TaskItem `isReminder = true`, `space = nil`, même `id` (les notifications planifiées et les deep links restent valides), puis le supprime. Vérifié sur simulateur avec un store V1.
- Étape 6a : espaces de démo semés une fois (`hasSeededSpaces`), aussi sur un store existant. Webentis en #30B0C7, sous-espaces à la couleur du parent. 8 couleurs et 12 symboles dans `SpaceStyle`.
- Étape 6a : un seul appel Foundation Models par dictée (intention + extraction + 3 espaces candidats) pour tenir la promesse des 3 secondes. Les chemins renvoyés sont rapprochés des vrais espaces (chemin exact, puis nom unique) ; espaces archivés exclus. Sans réponse d'espace du modèle, les candidats du routeur par mots-clés sont utilisés.
- Étape 6a : parser de secours. Intention : « rappelle-moi », « n'oublie pas », relance demandée → reminder ; « il faut que », « je dois », « à rendre », « devoir », « relancer », « finir », « préparer », « réviser »… → task ; sinon reminder si heure précise, task sinon. Espace : nom = 0,85, synonyme fort = 0,8, synonyme faible (« fin », « séance », « bug », « fields ») = 0,55, ancêtre trouvé aussi = +0,1, plusieurs branches = 0,5 max (question posée).
- Étape 6a : après « il faut que je / j' », le parser de secours remet le premier verbe à l'infinitif via une table de 30 verbes courants (finisse → finir, envoie → envoyer…) ; hors table, le mot reste tel quel.
- Étape 6a : toast de capture en bas, au-dessus de la barre d'onglets, 6 s (10 s s'il pose la question). Sous-ligne = « jour heure · phrase dictée ». Sous le seuil, la tâche est créée sans espace et le toast propose les 3 meilleurs candidats, complétés par les espaces les plus utilisés puis les racines, plus « Aucun ».
- Étape 6a : tâche dictée sans date = créée directement (« sans date ») ; rappel dicté sans date = formulaire comme en V1. Widget « Prochain rappel » : prochain élément daté, rappel ou tâche, préfixé « Rappel · » ou « Tâche · » (`WidgetSnapshot.Item.isReminder` optionnel pour relire les anciens instantanés). Réordonnancement du hub par appui long + glisser (`onMove`), archivage par balayage, section « Archivés » repliable avec Restaurer. Placeholders : colonne « Temps tracké » (6b), bloc Objectifs et lien Ajouter désactivé (6c), onglet Suivi (6b).
- Étape 6b : `Session.space` est optionnel dans le modèle (une relation to-one non optionnelle est fragile avec SwiftData et la suppression en cascade depuis Space) mais toujours renseigné par l'app. Démarrer une session clôt la précédente. Les sessions qui se chevauchent ne sont pas fusionnées (un log dicté sur une plage déjà trackée s'additionne).
- Étape 6b : Live Activity mise à jour localement (pas de push). Le chrono est un `Text(timerInterval:)` système, aucune mise à jour périodique. Stop = `StopSessionIntent` (`LiveActivityIntent`, exécuté dans le processus de l'app via le crochet `SessionControl.stop`) ; si le crochet est absent, la demande est déposée dans l'App Group et appliquée au retour au premier plan (`TrackingService.resume`). Au lancement et au retour au premier plan, l'activité est recréée ou fermée selon le store. Tap sur l'activité = `remindersint://tracking`.
- Étape 6b : voix. `sessionStart` (« je commence », « je me mets sur », « je démarre », « c'est parti »… sans date), `sessionStop` (« stop », « j'arrête », « fini », « pause »… phrase de 4 mots max ou contenant « session »), `sessionLog` (« j'ai fait / bossé / révisé… » + durée « 2h », « 1h30 », « 45 min », « une heure et demie »). Durée extraite avant la date pour que « 2h » ne soit pas lu comme 02:00. Moment : « ce matin » = 09:00, « hier soir » = 19:00 la veille ; sans moment, la session finit maintenant ; une session passée ne finit jamais dans le futur. Une session sans espace sûr demande l'espace dans le toast (sans « Aucun ») et n'est créée qu'au choix.
- Étape 6b : « Toujours sur … ? » 4 h après le début ; « Continuer » reprogramme 2 h plus tard, « Arrêter maintenant » clôt. « Rien tracké aujourd'hui » : notifications non répétées à 20 h pour les 7 prochains jours, celle du jour retirée dès qu'une session existe ; activé par défaut, interrupteur « Rappel du soir » dans Réglages.
- Étape 6b : stats. « 7 jours » et « 30 jours » sont glissants, aujourd'hui inclus (« 7 derniers jours », « 30 derniers jours ») ; moyenne = total / 7 ou 30 ; anneau et barres suivent. La semaine calendaire lundi-dimanche reste pour le hub et les objectifs hebdo. Anneau : 5 racines max, au-delà 4 + « Autres ». Série = plus longue suite de jours consécutifs (jusqu'à aujourd'hui ou hier) d'un espace racine ; « record personnel » si elle égale le record. Tuile Objectifs en placeholder (6c). Hub : « Temps tracké » = semaine en cours, delta vs semaine dernière au même moment.
- Étape 6c : champs ajoutés au modèle demandé : `isAchieved` / `achievedAt` (état atteint coché d'un outcome) et `counterPeriodStart` (un compteur hebdo ou mensuel repart de 0 à la période suivante, remise à zéro paresseuse à la lecture et au +1). Un outcome est enregistré avec `period = untilDate` et `target = 1`.
- Étape 6c : progression. hours = sessions de l'espace et de ses descendants sur la fenêtre (semaine calendaire lundi-dimanche, mois calendaire, création → échéance, ou création → maintenant). count = compteur de la période en cours. outcome = étapes faites / total pour la barre du hub ; atteint seulement quand l'utilisateur le coche. Vérifié sur la semaine du 28 sept. au 4 oct. 2026 avec une session coupée à minuit (self-test).
- Étape 6c : urgence = échéances non atteintes d'abord (la plus proche en tête), puis les objectifs périodiques les plus en retard sur leur rythme (part de la période écoulée − progression), les atteints en dernier. Le hub montre l'objectif le plus urgent du sous-arbre, sur toute la largeur de la carte.
- Étape 6c : le détail d'espace est une `List` : une carte de verre par objectif (et non une seule carte à lignes) pour le balayage « Archiver » natif. Tap sur le libellé = formulaire (modification, compteur ajustable, sous-étapes, archiver). « / Xh sem. » dans Suivi = somme des objectifs hours hebdo de la racine et de ses descendants. Pastille « Objectif » dans la Vue Jour : outcome non atteint dont l'échéance tombe dans les 7 jours, sur l'espace de la tâche ou un ancêtre.
- Étape 6c : tuile « Objectifs atteints n / m » : objectifs hebdo, mensuels et sans période évalués maintenant ; objectifs datés comptés si leur échéance n'est pas antérieure à la période affichée ou s'ils ont été atteints pendant. Tap = `GoalsOverview` (objectifs actifs groupés par espace, par urgence).
- Étape 6c : voix `goalProgress` (« j'ai signé », « … de plus », « encore un », « séance faite », « plus un », « +1 », sans date). Choix du compteur : un mot de 4 lettres ou plus du titre ou de l'unité dans la phrase (pluriel ignoré), sinon les espaces devinés (même sous le seuil), sinon tous les compteurs. Un seul candidat = +1 et toast avec « Annuler » (retire le +1) ; plusieurs = « Quel objectif ? » avec 4 puces max ; aucun = « Aucun objectif compteur ».
- Étape 7a : méthode par défaut « Musulmans de France 12° » sans décalage. Vérifiée à ±2 min sur le calendrier Bladi / Wadifa (UOIF 12°) des 31 août, 18 et 25 oct. 2026. Le site de la Grande Mosquée de Paris était inaccessible ; son calendrier de déc. 2024 (relayé par evous.fr) correspond au 12° avec des minutes de précaution constantes, Fajr −5, Dhuhr +5, Maghrib +2, Isha +4, Asr 0 : bouton « Préréglage Grande Mosquée de Paris » dans les réglages du module, vérifié à ±1 min sur 4 dates indépendantes de celle qui a servi à mesurer les décalages.
- Étape 7a : statuts. Coché avant la prière suivante = à l'heure, après = en retard (Isha : avant le Fajr du lendemain). Non coché à minuit = manquée (Isha : au Fajr suivant), matérialisé au lancement et au retour au premier plan (60 jours max, jamais avant l'activation). Cocher une manquée = rattrapée. Décocher supprime le record. Le menu contextuel d'une ligne force à l'heure / en retard / rattrapée / non faite.
- Étape 7a : stats. Série = jours consécutifs à 5/5 à l'heure ou en retard (une rattrapée ne compte pas dans la série), aujourd'hui compté une fois complet. « % ce mois » et la grille comptent les rattrapées : prières faites / prières déjà appelées ce mois depuis l'activation. À rattraper = toutes les manquées non rattrapées. La plus ratée = taux « à l'heure » le plus bas sur 30 jours glissants. Grille : 0 → 0,08, 1-2 → 0,3, 3 → 0,55, 4 → 0,8, 5 → 1.
- Étape 7a : notifications. Identifiants `prayer-AAAAMMJJ-<prière>-<k>` (k = 0 adhan, 1…8 relances, jusqu'à la prière suivante). Budget de 24 sur les 64 d'iOS : d'abord les 10 adhans des 48 h à venir, puis les relances les plus proches. Les tâches gardent 64 − 10 (suivi) − 24. `rescheduleAllPending` ne retire plus que les identifiants des tâches (il effaçait aussi les rappels du suivi). Titre « Asr · 16:12 », corps « Il est l'heure de la prière », sous-titre de relance comme les rappels, action « Fait », son coupé en mode discret.
- Étape 7a : widget et contrôle lisent un instantané App Group (prières d'hier à demain). Le contrôle « Prière faite » coche la dernière prière appelée non cochée : dans l'app via `PrayerControl.check`, sinon la demande est déposée dans l'App Group (avec son heure, pour le statut) et appliquée au retour au premier plan ; l'extension marque alors l'instantané et retire les relances de cette prière. Tap sur le widget = `remindersint://prayer` (ouvre l'espace).
- Étape 7a : voix `prayerCheck` : nom de prière (fajr / sobh, dhuhr / dohr / jumu'a, asr, maghrib, isha / icha) + mot de coche (fait, prié, ok, à l'heure, en retard, rattrapé). « rappelle-moi… » reste un rappel. « hier » / « d'hier » = la veille ; Isha dite avant le Fajr du jour = celle de la veille. Les règles priment sur Foundation Models, qui complète.
- Étape 7a : localisation. Paris par défaut tant qu'aucune position n'est choisie ; CoreLocation une fois à l'activation, sinon réglages ouverts sur la recherche de ville. Avec un App Group, SwiftData range le store dans le conteneur du groupe (`groupContainer: .automatic`).
- Étape 7b : l'écran de séance n'est pas une feuille : pendant une séance, le détail de l'espace Salle devient l'écran de la maquette 12 (barre d'onglets, micro et toast restent visibles). Une séance = une Session du suivi : le Stop de la Live Activity la termine aussi. La Live Activity de session porte en plus l'exercice, la dernière série et la fin du repos.
- Étape 7b : PR. Une série est un record si elle bat tout ce qui précède sur l'exercice : charge plus lourde, 1RM estimé plus haut, ou plus de reps à une charge déjà faite (plus de reps / de durée / de distance pour les autres types). Les toutes premières séries d'un exercice ne sont pas des records. Recalculés dans l'ordre chronologique à chaque ajout, modification ou suppression. Le résumé de fin ajoute le record de volume d'une séance par exercice.
- Étape 7b : repos = `restSeconds` de l'exercice (90 s en séance libre), démarré à chaque série ; notification « Repos terminé », sans bannière quand l'app est ouverte. « + » copie la dernière série du jour, sinon la dernière jamais faite, sinon la cible du programme.
- Étape 7b : une séance terminée hors de l'app (Stop de la Live Activity, « Arrêter maintenant », « j'arrête ») garde `summaryShownAt` vide ; son résumé s'ouvre en feuille au prochain retour au premier plan, une seule fois (séances terminées dans les 12 dernières heures). « Terminer » et « fin de séance » le marquent comme vu ; « Annuler » sur une fin de séance le remet à vide.
- Étape 7b : voix. Règles d'abord (alias FR / EN, l'alias le plus long gagne : « leg curl » avant « curl ») ; Foundation Models complète l'exercice, la charge, les reps ou le programme. « 85 5 » = charge puis reps ; « 100 pour 3 » ; « 85 kilos 5 reps » ; « 82,5 kg ». Une série sans séance en cours démarre une séance libre. « Je commence la séance » sans programme = programme suggéré. Annuler : supprime la série, revient à l'exercice précédent, rouvre la séance ou annule le démarrage.
- Étape 7b : stats du module. Fréquence = séances des 8 dernières semaines / 8. Série = jours depuis le début de la suite d'entraînements en cours, 2 jours de repos d'affilée au plus. Grille : volume du jour / volume du jour le plus chargé, 0,2 minimum pour un jour d'entraînement.
- Étape 7b : objectifs. Un compteur dans un espace Salle (ou un descendant) compte tout seul les séances de sa période. `prWeight` = charge max de l'exercice (record) face à la cible, période « sans » ou « jusqu'à une date ». Goal garde l'`exerciseID` et non une relation : une relation Goal → Exercise faisait vider par SwiftData le lien exercice des entrées de séance de cet exercice (vérifié sur simulateur).
- Étape 8a : store. `SchemaV1` (VersionedSchema) + `AppMigrationPlan` vide ; URL explicite `Library/Application Support/default.store` du conteneur App Group, sinon Application Support. Store illisible : renommé `default.store.broken-<date>`, store vide recréé, alerte au lancement ; jamais de crash. Données de démo uniquement en DEBUG sur `-seedDemoData YES`. Notifications : `NotificationBudget` applique les 64 d'iOS à chaque ajout (prières du jour et adhans, puis rappels par échéance, relances, « Rien tracké »). Localisation en précision réduite, coordonnées arrondies à 2 décimales.
- Étape 8b : parsing dans le fuseau de l'appareil (`Calendar.parsing`). Foundation Models : mode simplifié seulement si le modèle manque ou ne gère pas la langue (y compris l'erreur générique qui enveloppe le gestionnaire de modèles, au simulateur) ; toute autre erreur est relancée une fois puis la phrase passe par le parser de secours. Pendant une séance, une série dictée exige un exercice de la bibliothèque ou un motif explicite (« 80 x 8 », « série », « reps »). Rien n'est planifié avant la réponse à la demande d'autorisation des notifications (file d'attente dans `NotificationBudget`) ; tout est replanifié au premier plan si l'autorisation arrive plus tard. Bandeaux « activer » pour notifications, micro et dictée refusés. Dictée uniquement sur l'appareil, session audio toujours libérée, `rawTranscript` gardé en DEBUG seulement (vidé une fois en release).
